# 0039. The email record, the reply mode and the gate

- Status: Superseded
- Date: 2026-11-22
- Affects: packages/db, packages/inbox, packages/auto-reply, apps/api, apps/worker, apps/platform, docs/overview/README.md, docs/plans/0001-auto-reply-roadmap.md
- Superseded by: [0064](0064-skipped-emails-are-not-kept.md)

## Context

[0021](0021-channels-and-channel-accounts.md) says that the owner of a message is the owner of the channel account it arrived on, and the overview says that a gate in code decides whether a message is handled. Nothing stores a message yet. The user must be able to see in the dashboard which emails the assistant received, where each one stands in the pipeline and why it was or was not handled. The playbook also has to say whether a reply is saved as a draft for approval or sent at once.

## Decision

- A **message record** is a row of `messages`. It holds the owner, the channel account (set to null when the account is deleted), the channel and provider names, the provider's message id and thread id when it gives them, the sender, the recipients, the subject, the body, the time the provider received the message, two flags derived from the headers (`isReply` and `isBulk`), a `status`, a `statusReason` and the time of each change. It never holds attachments, raw headers or credentials. The body is cut to `MESSAGE_BODY_LIMIT` characters, which is 20,000, and `bodyTruncated` says that it was cut. A subject is cut to 500 characters.
- A message is unique on the user, the channel, the provider and the provider's message id. That tuple is its idempotency key. Recording a message that exists changes nothing, and publishes `email.received` again only while the stored status is still `received`, so a lost publish is repaired by delivering the message again.
- The `status` values are `received`, `not_applicable`, `queued`, `processing`, `drafted`, `sent` and `failed`. A status only moves forward: `received` to `not_applicable`, `queued` or `failed`, `queued` to `processing` or `failed`, and `processing` to `drafted`, `sent`, `not_applicable` or `failed`. `not_applicable`, `drafted`, `sent` and `failed` are final. A step that changes the status uses the conditional update in `@leren/inbox`, which writes only when the stored status allows the move, so a repeated or late message cannot move a record backwards. `statusReason` is a short code that says why, such as `no_active_playbook` or an `EmailVerdict` reason.
- Stages after the gate set the status as the pipeline passes through them: the runner sets `processing`, and the stage that ends the run sets `drafted`, `sent` or `failed`. A later decision adds a state when a stage needs one, such as an abstention or an escalation.
- A new package, `@leren/inbox`, holds the message types, the truncation, the status transitions, the queue names `email.received` and `email.process`, and the function that records a message and publishes it. The API and the worker both use it, and neither imports the other.
- The gate is a worker job that consumes `email.received`. It loads the message and ends the work when the status is not `received` or `queued`. It then takes the playbooks of the message's owner whose email conditions name the message's channel account and which are usable according to `isKnowledgeUsable`, and evaluates each one with `evaluateEmailConditions`. The mailbox owner is the label of the account, and the names are taken from the user's profile. A message that no playbook handles is set to `not_applicable` with the reason of the first skip, or `no_active_playbook` when no playbook was usable. A message that at least one playbook handles, or may handle after a mention check, is set to `queued` and published to `email.process` with the playbook ids and their verdicts. An account that is revoked is treated like no playbook. The gate does no model call. A verdict `check_mention` goes to the pipeline for the mention check, because the check needs a model.
- Every email playbook has a **reply mode** in its email conditions, `draft` or `send`, and its default is `draft`. The product decision is [0001](../product/0001-reply-mode-draft-or-send.md). In `draft` the reply waits for the user to approve it. In `send` the reply is sent when the Reply Agent produces it and no policy blocks it. The mode is read when the reply is made, so a change applies to messages that have not reached that step. The assistant's tools cannot set the mode, because no code enforces its confirmation (0036) and `send` takes an action that cannot be undone. The user sets it in the Rules tab, and a playbook the assistant creates is in `draft`. The migration sets `draft` on the stored email conditions.
- `GET /api/messages` returns the signed-in user's records, newest first, filtered by `status`, `channel` and `channelAccountId`, with cursor paging. `GET /api/messages/:id` returns one. Both are scoped by the session's user. They return only the message record and never credentials.
- `POST /api/messages/simulate` records a message as if the provider had delivered it to the user's account on a development provider. It exists only while the `mailpit` provider is enabled, which the API already refuses in production. A provider that reads a real mailbox is a separate decision and is not part of this one. It publishes through the same function that such a provider will use.

## Consequences

- The dashboard reads one table for the log of messages, the counts by outcome and the failures, and builds no state of its own.
- The record keeps a truncated copy of the message for as long as the user keeps it. Deleting the user deletes the records. Retention and deletion by the user are not built.
- A late stage cannot overwrite a final status, so a retried job that has already finished does nothing.
- The mode `send` depends on the sending stage that is built later. Until then every reply is a draft, whatever the mode says.
- The roadmap item that lists `threads`, `decisions` and `drafts` for this feature is replaced. A thread is the provider's thread id on the record, and the decision and the draft belong to the Reply Agent and the approval stages.
- The mention check of a playbook that asks for it moves to the pipeline, because the overview placed it in the gate and the gate makes no model call.

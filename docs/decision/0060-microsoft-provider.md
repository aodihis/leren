# 0060. Microsoft as the second channel provider

- Status: Accepted
- Date: 2026-11-26
- Affects: packages/channels, apps/api, apps/worker, .env.example, docs/overview/README.md

## Context

[0038](0038-channel-providers-and-google-oauth.md) names Microsoft Graph as the next provider after Google. Many users keep their mailbox in Microsoft 365, including users whose address is on a company domain, and personal Outlook.com mailboxes use the same API. The listener of [0041](0041-email-listener-cursor-and-unreadable-mail.md) and the deliverer of [0046](0046-reply-delivery.md) work through the `EmailProvider` and `EmailSender` interfaces, so a second provider is one adapter. Microsoft differs from Google in three ways that the existing decisions assume away: it cannot revoke the tokens of one application, it replaces the refresh token on every refresh, and it assigns the `Message-ID` of a reply itself.

## Decision

- The provider's name is `microsoft`, its channel is `email` and its display name is "Microsoft". Its variables are `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET`, and `CHANNEL_TOKEN_ENCRYPTION_KEY` is required when it is enabled. The redirect URI is `${API_URL}/api/channel-accounts/microsoft/callback`.
- The application is registered in Microsoft Entra ID for accounts in any organisation and for personal Microsoft accounts. The adapter uses the `common` tenant, so work, school and personal mailboxes connect through the same flow. The tenant is not configurable.
- The adapter uses the authorization code flow with PKCE against `https://login.microsoftonline.com/common/oauth2/v2.0`. The scopes are `openid`, `email`, `profile`, `offline_access`, `https://graph.microsoft.com/Mail.ReadWrite` and `https://graph.microsoft.com/Mail.Send`. `offline_access` makes Microsoft return a refresh token, and `Mail.ReadWrite` lets the product read mail and create drafts. The request uses `prompt=select_account`, so the user chooses the mailbox to connect.
- The provider's identifier of the account is the `tid` claim and the `oid` claim of the ID token, joined by a colon, because the object id of a user is unique only within its tenant. The display label is the address of the mailbox, read from Graph `/me` as `mail`, or as `userPrincipalName` for an account without one, because the sign-in name of a work account can differ from its address and the deliverer compares the label with senders and recipients so that the account never answers itself. The ID token is read without a signature check for the same reason as the Google one: it comes directly from the token endpoint over TLS.
- `refresh` returns the refresh token that Microsoft sends with every refresh, and `getAccessToken` stores it as it stores any refreshed credentials. An answer of `invalid_grant`, `interaction_required` or `consent_required` throws `InvalidGrantError`, so the account becomes `revoked`, because only a new connection can satisfy a requirement to sign in or consent again.
- Microsoft has no endpoint that revokes the tokens of one application. `revoke` therefore calls nothing, and disconnecting deletes the account as 0038 describes. 0038's revocation at the provider still applies to Google. For a Microsoft account the user removes the application's permission in their Microsoft account settings.
- Every Graph request sends `Prefer: IdType="ImmutableId"`, so the id of a message stays the same when it moves between folders. The provider message id of an email, the id of a draft and the id of a sent reply are all immutable ids.
- The cursor is the Graph delta link of the `Inbox` folder's messages. At the connection the adapter requests a delta of the inbox filtered on `receivedDateTime ge` the current time, reads every page, and stores the final delta link as `sync_cursor`. The delta link keeps the filter, so a later change to a message that was already in the mailbox, such as marking it read, is never returned, and the listener never answers mail that arrived before the connection.
- `fetchNewMail` follows the delta link, reads every page and stores the new delta link as the cursor. It ignores entries that report a removed message and messages whose `isDraft` is true. It reads each remaining message in full with `Prefer: outlook.body-content-type="text"`, so the body is plain text. A message that Graph reports as not found is skipped, and a message that cannot be converted is listed in `unreadable`, as 0041 describes. When Graph answers that the delta link can no longer be resumed, the adapter requests a new delta from the current time and returns it as a baseline, which the poll records as a gap.
- The adapter turns a Graph message into an email. The sender, the recipients and the copied recipients are the `emailAddress.address` values of the message. The provider thread id is the `conversationId`. `isReply` and `isBulk` are read from `internetMessageHeaders` with the same rules as for Gmail. Graph omits these headers for mail that never left the organisation, and such a message is then neither a reply nor bulk.
- A reply is delivered in three steps: `POST /me/messages/{id}/createReply` on the original, then `PATCH` of the new message to set the recipient from the record, the subject and the plain-text body, then, in `send` mode only, `POST /me/messages/{id}/send`. In `draft` mode the id of the message is the `mailbox_draft_id`. In `send` mode it is the `sent_message_id`. When a step after `createReply` fails, or `send` is known not to have happened, the adapter deletes the draft. The delivery may be retried only when the deletion succeeded. Otherwise it ends as `rejected`, so a retry never leaves a second draft. When the answer to `send` is lost, the outcome is unknown, as 0046 describes, and the draft is left as it is.
- Exchange assigns the `Message-ID` of a reply and sets its `In-Reply-To` and `References` headers from the original. The `messageId` that the deliverer builds is therefore not used by this adapter, and the reply is found by its immutable id instead. The adapter reads only the `Reply-To` address and the `Message-ID` of the original.
- `OutboundReply` carries the provider's id of the original, because `createReply` needs it.
- A delivery request that does not reach Graph, or that Graph answers with status 401 or 429, throws `DeliveryNotSentError`. An answer with status 403 throws `DeliveryRejectedError` with the reason `forbidden`, and any other answer from 400 to 499 throws it with the reason `rejected`. Any other failure has an unknown outcome, as for Gmail, so a reply is never sent twice.

## Consequences

- An administrator of a work or school tenant that does not allow users to consent to mail permissions must approve the application once before its users can connect. Serving other organisations also needs Microsoft publisher verification, which is outside this decision.
- A user who disconnects a Microsoft account keeps the application's permission until they remove it themselves. The overview tells them where to do it.
- Delivering a reply takes up to three requests instead of one, so a delivery stays `started` for longer and a failure between the steps costs an extra request to delete the draft.
- Mail that a rule of the user moves out of the inbox before the poll is not ingested, as with Gmail.
- The listener polls, as 0041 decides. Graph change notifications can later trigger the same poll job, because the delta link is already the cursor that Graph's notifications are designed to work with.
- Mailboxes that only offer IMAP and SMTP, such as Proton Mail through its Bridge, are not covered by this provider and need their own decision.

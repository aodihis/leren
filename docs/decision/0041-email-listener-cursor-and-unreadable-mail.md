# 0041. The email listener: cursor at connection and unreadable mail

- Status: Accepted
- Date: 2026-11-22
- Affects: packages/channels, packages/db, packages/inbox, apps/api, apps/worker, .env.example, docs/overview/README.md, docs/plans/0001-auto-reply-roadmap.md, docs/rules/packages.md

## Context

[0040](0040-email-listener-and-polling.md) decides that the worker polls a mailbox and that the first poll of an account stores the position of the mailbox without reading mail. Building it showed three points that the decision gets wrong or leaves open. Mail that arrives between the connection and the first poll is lost, because the first poll stores a position that is already past it. One message that cannot be converted to an email stops every later poll, because a retry cannot fix it and the cursor never advances past it. The provider reads the mailbox with an access token, and the poller already has one from `getAccessToken`. This decision replaces 0040 and states the whole listener, so that one record describes it.

## Decision

- A new package, `@leren/channels`, holds the channel provider interface, the registry, the Google and Mailpit adapters, the encryption of credentials, the function that returns a valid access token for an account and the checks of the provider environment variables. `apps/api` and `apps/worker` both use it. The API's connection routes and their behaviour are unchanged.
- An email provider implements `EmailProvider`, which extends `ChannelProvider` with one operation, `fetchNewMail(accessToken, cursor)`. It returns a `FetchResult`: the new messages as emails in the shape that `@leren/inbox` records without the owner, the account, the channel and the provider name, the cursor to resume from, a `baseline` flag, and the ids of the messages it could not convert in `unreadable`. A provider that cannot read a mailbox, such as `mailpit`, does not implement it, and the poller skips its accounts.
- `channel_accounts` gets a nullable `sync_cursor` text column. The cursor is opaque to everything except the provider that wrote it. For Google it is the Gmail `historyId`.
- The listener **polls**. It needs no public endpoint, no Pub/Sub topic and no watch renewal, and a missed poll is repaired by the next one. A timer in the worker publishes `email.poll` every `EMAIL_POLL_INTERVAL_SECONDS` seconds, which is 60 by default, once for each account that is active and whose provider is enabled and can read a mailbox. The message carries the time of the request. The job drops a poll that is older than two intervals, so a worker that was down does not run a backlog. The job for one account is idempotent.
- The poll job of an account loads a valid access token, calls `fetchNewMail`, records each email with `recordInboundEmail`, and then stores the new cursor. The cursor is stored after every email is recorded, so a failure repeats emails that are already recorded and loses none. Recording is idempotent, so repeating an email changes nothing. The cursor is written only when the stored cursor is still the one the job read, so overlapping polls of the same account never move it backwards.
- A message that the provider reports as not found, because it was deleted after it arrived, is skipped. A message that the provider cannot convert to an email is skipped, listed in `unreadable` and logged as a warning with its id, because a retry cannot fix it and it would stop every later poll. Any other failure to read a message fails the job, which the queue retries, and the cursor does not advance.
- **Connecting an account stores the position of the mailbox at that moment as `sync_cursor`.** The Google adapter reads it from the Gmail profile when it finishes the connection, and the API saves it with the account. This applies when an account connects again after it was revoked or disconnected. The listener therefore ingests **only mail that arrives after the account is connected**, including mail that arrives before the first poll, and it never answers mail that was already in the mailbox.
- When the provider cannot read the position at the connection, the account is saved with a null cursor. The first poll of an account with no cursor stores the current position and records nothing, so the account is connected and only that first window of mail is lost.
- If Gmail answers that the stored `historyId` is too old to resume from, the poll stores the current `historyId`, records nothing for the gap and logs a warning. Mail that arrived during the gap is not ingested.
- The Google adapter lists new messages with `users.history.list`, using `labelId` `INBOX` and `historyTypes` `messageAdded`, and reads every page of the response. The new cursor is the top-level `historyId` of the last page. It then reads each message in full. It skips a message that carries the `SENT` or `DRAFT` label, so the account's own mail is never ingested. It uses the `gmail.readonly` scope that 0038 already requests.
- The adapter turns a Gmail message into an email. The body is the `text/plain` part, or the text of the `text/html` part when there is no plain text. Attachments are ignored. The provider message id and thread id are the Gmail ids. The sender, the recipients and the copied recipients are the addresses of their mailboxes: the address in angle brackets when a mailbox has one, and never an address that is written in a display name. `isReply` is true when the headers carry `In-Reply-To` or `References`. `isBulk` is true when the headers carry `List-Unsubscribe`, `Precedence` of `bulk`, `list` or `junk`, or `Auto-Submitted` other than `no`. Truncation is applied by `recordInboundEmail`, not by the adapter.
- The worker reads the same configuration as the API for providers: `CHANNEL_PROVIDERS`, the variables of each enabled provider and `CHANNEL_TOKEN_ENCRYPTION_KEY`. Both use the same checks, so they fail at startup under the same conditions. The refresh of a token by the worker and by the API can overlap. The last write wins, and both writes hold a valid token.
- When the provider rejects the refresh token, `getAccessToken` marks the account `revoked`, as it does today, and the poll ends without error. A revoked account is not polled again until the user connects it again.
- `mailpit` stays a provider for development without a listener. A developer injects mail with `POST /api/messages/simulate`.

## Consequences

- The poller delays a message by at most one interval plus the time to process it. A shorter interval costs more Gmail quota and a longer one delays replies.
- A message that arrives while the account is disconnected, revoked or in a gap is not ingested later. The overview states this.
- A message that cannot be converted is not ingested and is never retried. The warning with its id is the only trace of it.
- Moving the provider code into `@leren/channels` changes imports in `apps/api` and adds a package to `docs/rules/packages.md`.
- Gmail push notifications are not used. A later decision can add them in front of the same poll job to reduce delay, and it does not change the record or the gate.
- `gmail.readonly` is a restricted scope (0038). Until the Google project is verified, only listed test users can connect, and their refresh tokens expire after seven days, so the poller of a test account stops until the user connects it again.

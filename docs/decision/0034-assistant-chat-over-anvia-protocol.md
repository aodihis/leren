# 0034. The assistant chat uses Anvia's client protocol and Anvia memory, and confirms writes in the conversation

- Status: Superseded
- Date: 2026-11-21
- Affects: apps/api, apps/platform, packages/assistant-agent, packages/db, prompts/assistant.md, docs/overview/README.md, docs/rules/backend.md, docs/rules/frontend.md
- Superseded by: [0036](0036-playbooks-enabled-or-disabled.md)

## Context

[0032](0032-assistant-writes-with-confirmation.md) lets the Assistant Agent create and change rules and knowledge after the user confirms. It asks for two confirmations: one in the conversation, and one from the agent runtime that pauses the run on every write tool. The runtime pause needs the server to store the suspended run and a second request type to resume it, and the chat would need its own conversation table and history format.

Anvia provides what the chat needs: `@anvia/server` and `@anvia/client` for the streaming protocol, `@anvia/react` for `useChat`, and `@anvia/memory-drizzle` for conversation storage in PostgreSQL.

## Decision

- The chat is one route, `POST /api/assistant/chat?sessionId=`. It accepts only `messages` requests of Anvia's client protocol (`parseClientStreamRequest`) and answers with `createClientStreamResponse` over `agentToClientStream`. The platform uses `useChat` with `createHttpClientTransport`.
- A conversation is the agent's memory for a session id. The client chooses the id of a new conversation. The memory store is `DrizzleMemoryStore` with the user id in its key, so one user's session id never reaches another user's messages. Its tables, `agent_memory_*`, are generated by `anvia-memory-drizzle init` and migrated with the rest of the schema. There is no table of our own.
- When memory is on, the agent receives only the newest user message, because the store holds the earlier turns. The conversation's title is stored in the session metadata, which also marks the session as an Assistant Agent conversation. The history list and the stored messages come from `GET /api/assistant` and `GET /api/assistant/conversations/:sessionId`.
- The agent confirms every write in the conversation: it shows what it will save and calls a write tool only after the user says yes. This is a rule in the assistant prompt. The runtime pause on write tools, `approvalTools`, is removed from the Assistant Agent. This replaces that part of [0032](0032-assistant-writes-with-confirmation.md).
- Everything else in [0032](0032-assistant-writes-with-confirmation.md) stays in force: the write tools and scopes, saving through the same services as the web API, knowledge saved as a draft and approved only by the user, no approve, archive or delete tool, and the audit log.

## Consequences

- The chat has no custom wire format, no conversation table and no stored suspended run, and the platform needs no code to read the stream.
- Confirmation is the model following its prompt, not a mechanism. A model that ignores the prompt could write without asking. The write is limited to what the tools allow: drafts of knowledge, and rules the user can see and edit in the interface.
- The memory tables hold the Assistant Agent's messages as Anvia stores them, so their format follows `@anvia/memory-drizzle`.
- Deleting a conversation clears its memory. Only the session id and the user decide which messages the agent sees.
- Confirmation in code is an open question. The roadmap lists it under F10 as a follow-up. A stored rule or knowledge text that the agent reads could try to talk the model into writing, so the options to weigh are a runtime approval on the write tools, which needs a stored suspended run, or a write that takes effect only after a click in the interface.
